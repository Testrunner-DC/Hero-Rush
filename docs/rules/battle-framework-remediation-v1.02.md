# 对战框架整改与验收计划（规则 1.02）

> 面向角色：项目经理、产品、开发、测试
> 2026-08-28 更新：GrandUMI 基本型 V2 框架已进入 `2.0.0-framework-rc1` 统一验收，P0-01 至 P0-07 的框架能力及 P0-08 准入机制已落地。生产卡牌效果覆盖仍为 0/290，因此“框架可验收”与“线上卡池可发布”必须分开管理；当前线上 V2 仍为 No-Go。
>
> 实施总方案：以 GrandUMI 为结构基本型的 V2 旁路重构，见 [Hero-Rush 对战框架重构方案](../BATTLE_FRAMEWORK_GRANDUMI_V1.02_PLAN.md)。

## 2. P0 整改包

### P0-01 权威开局与调度

实现要求：

- 服务端创建游戏后进入 `SETUP`，不能直接设为完成。
- 随机或按房间约定确定先攻玩家，并把“先攻身份”存为稳定字段，不能用座位号推断。
- 双方抽 6；先攻先提交调度，后攻后提交。
- 被调度卡放牌库底，补等量卡，再洗混。
- 双方完成后才进入先攻玩家的回合开始。

验收：

- 两个座位分别成为先攻时均通过同一组测试。
- 后攻不能在先攻提交前完成调度。
- 调度 0—6 张的牌数守恒、区域正确、随机种子可复现。

### P0-02 显式状态机

建议的最小权威状态：

`SETUP → TURN_START → DRAW → ACTION → BATTLE_ADJUST → BATTLE_TARGET → BATTLE_RESPONSE → BATTLE_JUDGMENT → TURN_RESPONSE → END`

实现要求：

- 战斗中的目标、应对、判定必须是可恢复、可广播的状态，不能在一次命令中瞬间全部结算。
- 单次战斗结束后回到战区攻击顺序；整个战斗阶段结束后进入独立 `TURN_RESPONSE`。
- 状态转换只由服务端规则命令触发，客户端不能指定任意目标阶段。

验收：

- 每个状态均有允许命令白名单和拒绝测试。
- 断线重连后能恢复当前攻击者、目标、优先玩家、连续放弃次数和剩余应对号召次数。

### P0-03 统一命令合法性

实现要求：

- 所有命令验证：操作者、阶段、来源区域、控制权、目标集合、最少/最多目标数、次数和费用。
- `SELECT_TARGET` 只能选服务端生成的候选集。
- `MOVE_CHARACTER` 校验角色实际所在区域、本回合入场状态和每卡次数。
- 服务端拒绝原因使用稳定错误码，客户端只展示结果。

验收：

- 对每个命令至少覆盖：合法、错误玩家、错误阶段、伪造来源、伪造目标、超次数。
- 模糊测试生成的非法命令不得改变状态哈希。

### P0-04 号召与战区调整

实现要求：

- Lv4+ 号召的撤退 Lv 总和必须等于目标 Lv，不能大于。
- 盖卡按 Lv1 计入且正确进入撤退区。
- 首回合次数按先攻身份判断。
- 战区调整提交一个原子布局，最多涉及 4 张战区角色；不计为移动，也不允许借此进出基地。

验收：

- Lv 支付不足、超额、恰好三类用例。
- 四个战区满员时可合法互换，重复卡、丢卡、容量超限均被拒绝。

### P0-05 战斗、距离与应对

实现要求：

- 按战区图计算距离；R0 不能攻击。
- 目标只能是 R 内敌方角色或能力允许的破绽。
- 攻击机会、跳过攻击和【追击】统一记录。
- 目标产生后进入应对窗口，由非回合玩家先行动；双方连续放弃才关闭。
- 原目标失效且有其他合法目标时回到目标步骤；没有合法目标或攻击者无效时结束该次战斗。
- 应对号召在“每次战斗应对步骤”和“回合应对阶段”分别计数。

验收：

- 覆盖所有六个战区节点的距离矩阵。
- 覆盖目标移出 R、目标撤退、攻击者撤退、攻击者 R 变 0、出现新合法目标。
- 覆盖非回合玩家先行、交替优先权、连续两次放弃、双方各一次应对号召。

### P0-06 效果队列与状态检查

实现要求：

- 建立统一的待处理效果队列，支持同一时点排序、双方先后、嵌套触发和结算后状态检查。
- 每个原子效果后执行规则状态检查：战力为 0 的角色锁定并撤退、胜负条件、区域容量与结附跟随。
- 数值采用“原本/替换/增减/期限”的可重算模型，R 和 Lv 下限允许为 0。
- 结束时点按 1.02 的错过时点和新生回合效果立即结束处理。

验收：

- 触发顺序由有权玩家选择，不能依赖数组插入顺序。
- 战力归零、同时归零、效果中途归零和结附宿主离场均有测试。
- 数值效果到期、翻面、离场再进入、失去效果均可重算。

### P0-07 结束弃牌

实现要求：

- 手牌超过 9 时进入服务端等待选择状态。
- 回合玩家选择准确数量的手牌舍弃，卡牌进入拥有者撤退区。
- 完成弃牌及衍生效果后才切换回合。

验收：

- 9 张无需操作；10 张选择 1；多张选择顺序、触发效果及断线重连可恢复。

### P0-08 构筑与卡牌覆盖门禁

实现要求：

- 主卡组按角色名称合计最多 3 张，而非按印刷编号。
- 上线卡池中存在效果文本但没有实现的卡必须被构筑服务拒绝，或明确进入“不可用卡池”。
- 每张可用卡的效果实现需要关联卡号、规则引用和自动化测试。

验收：

- 同名不同编号合计第 4 张被拒绝。
- 50/9 张数、双色限制和名称限制均由服务端复核。
- CI 输出“有效果卡总数、已实现数、缺失列表”；缺失卡不能静默进入线上对局。

## 3. 分批交付顺序

### A：状态机地基

P0-01、P0-02、P0-03。先把权威状态和命令边界定死，避免后续规则继续堆在不可恢复的一次性流程上。

### B：核心对战

P0-04、P0-05、P0-07。完成号召、调整、距离、目标、应对、判定和结束弃牌的闭环。

### C：效果系统

P0-06，并迁移现有已实现卡牌到统一队列；禁止新卡继续写旁路逻辑。

### D：卡池准入

P0-08。先以“可用白名单”发布，再逐批扩大卡池；每批必须有覆盖率报告。

## 4. 发布门禁

以下条件全部满足才可关闭“对战框架 P0”：

- 官方 1.02 主流程端到端测试通过。
- 双方座位、先后手和断线重连均通过。
- 非法客户端命令不会改变权威状态。
- 固定随机种子下可重放并得到相同状态哈希。
- 引擎单测、服务端集成测试和至少一条双客户端冒烟测试通过。
- 可用卡池不存在“有文本但无实现”的静默卡牌。
- 测试报告按规则编号列出覆盖情况，不能只报告用例数量。

## 5. 暂不混入本轮的项目

- UI 动画、特效、观战、排行榜等体验项不应阻塞规则框架整改。
- 扩充全部卡牌效果在状态机稳定后分批进行，但线上卡池必须执行白名单门禁。
- 旧版规则截图与旧 OCR 文档只作历史依据，不能用于新增实现。

## 6. PM 跟踪字段

每个整改任务至少记录：

- 对应规则编号。
- 权威状态/命令变化。
- 正向与反向验收用例。
- 数据迁移或兼容影响。
- 完成证据（测试名称、构建结果、提交号）。
- 是否改变线上协议；若改变，客户端和服务端必须同批发布。
