# Hero-Rush × Legion12 对战体验差距审计

日期：2026-08-29
范围：对战大厅、单人规则沙盒、正式对战界面
原则：参考 Legion12 的信息架构与交互闭环，不复制其术语、规则区域或视觉色调。

## 结论

Hero-Rush V2 已具备可执行的 1.02 权威规则内核、固定方向双边沙盒和基本对战操作，但当前界面仍属于“内核演示层”，距离可长期使用的对战产品还有明显差距。Legion12 的核心优势不是面板数量，而是完整闭环：大厅确认身份与规则 → 房间整备 → 进入对局 → 就地执行动作 → 常驻事件反馈 → 断线/结束/回放。

当前最重要的缺口有三项：

1. 好友房没有“整备室”状态，创建/加入后直接等待匹配，缺少双方信息、卡组锁定、准备、离开和房主规则确认。
2. 沙盒 GM 目前只是少量本地快捷操作，尚未达到 Legion12 的全区域调度、阶段跳转、卡牌增删移动、数值修正与可复现导出。
3. 对局动作主要集中在底部全局条，缺少卡牌附近的上下文操作、完整事件记录、攻击/响应聚焦和结束态闭环。

## 一、大厅对照

### Legion12 已形成的闭环

- 大厅先显示当前卡组和模式，再进入具体工作区。
- 好友房创建前可配置观战、手牌公开和规则模式。
- 创建后进入独立整备室，显示双方在线、卡组选择、准备状态、房间码复制、离开和编辑卡组。
- 创建、加入、观战是三个明确入口，不混为一个提交表单。
- 登录身份、服务器状态和错误反馈在操作前可见。

### Hero-Rush 当前问题

| 优先级 | 问题 | 影响 | 所需层级 |
| --- | --- | --- | --- |
| P0 | 好友房没有整备室与准备状态 | 用户无法确认双方卡组和是否已经准备，房主也不能撤销或调整 | 协议、服务端、前端 |
| P0 | 没有离开/关闭好友房的显式流程 | 只能靠刷新或连接变化退出等待 | 协议、服务端、前端 |
| P1 | 没有房间码复制和双方在线状态 | 邀请与等待过程反馈不足 | 前端，部分协议 |
| P1 | 没有房主规则摘要 | 无法在开局前确认本局特殊规则 | 协议、服务端、前端 |
| P1 | 管理后台曾作为大厅主操作暴露 | 普通玩家信息层级被开发入口干扰 | 前端；本轮已移除 |
| P2 | 卡组预览使用随机五张正面图，不能表达“主卡组＋冲击卡组” | 视觉噪音大，卡组结构不清楚 | 前端；本轮已改为两类官方卡背 |

### 大厅验收目标

- 好友房创建后必须进入整备室，而不是只显示等待文字。
- 双方均可看到姓名、在线状态、卡组是否锁定、准备状态；对手卡组内容保持隐藏。
- 房主可复制房间码、关闭房间；加入者可离开房间。
- 只有双方准备后服务端才能创建对局。

## 二、沙盒对照

### Legion12 的有效机制

- 正常画面始终是固定方向的双边全信息战场，控制权自动跟随当前行动者或待处理提示。
- GM 面板是额外工具，不承担正常对局操作。
- GM 可针对任一玩家设置阶段与回合、添加卡牌、移动手牌、无视费用打出、操作场上卡牌、调整数值、抽牌、磨牌、洗牌并发起测试进攻。
- GM 指令由服务端校验并进入对局记录，可导出 JSON 复现。
- 放置卡牌时由 GM 面板“武装操作”，随后直接在战场点击目标区域完成。

### Hero-Rush 当前问题

| 优先级 | 问题 | 影响 | 所需层级 |
| --- | --- | --- | --- |
| P0 | GM 只有重建、跳过调度和抽牌 | 无法构造绝大多数规则测试局面 | 内核、沙盒命令层、前端 |
| P0 | GM 原子操作直接在浏览器内修改状态 | 无法证明与线上权威执行完全一致，也没有权限边界 | 服务端沙盒会话与协议 |
| P0 | 没有保存/导出/重放沙盒记录 | Bug 场面无法稳定交接给开发者复现 | 服务端存储、协议、前端 |
| P1 | 不能从卡池选卡并放到指定区域 | 卡效测试需要依赖随机抽到目标牌 | 沙盒卡池选择器、命令层 |
| P1 | 不能跳转阶段、指定行动玩家 | 测试战斗/结束阶段成本过高 | 沙盒命令层、前端 |
| P1 | 不能修改卡牌战力、移动、撤退、结附状态 | 已有原子能力没有被 GM UI 完整暴露 | 内核封装、前端 |
| P2 | GM 打开后遮挡右侧战场 | 调度时仍需观察目标区域 | 前端可拖动/压缩或临时收起 |

### 沙盒验收目标

- 不切换席位；上下玩家方向固定，双方手牌和覆盖卡信息均公开。
- 当前合法操作自动归属于规则指定玩家。
- GM 默认关闭，通过按钮或 `T` 打开。
- GM 至少覆盖：设置回合/阶段、抽牌、洗牌、添加卡牌到五类区域、移动/撤退/结附、增减战力、直接建立攻击场面、导出记录。
- 所有 GM 操作产生带 revision 的事件并可重放。

## 三、正式对战界面对照

### Legion12 的有效机制

- 1440×900 单一舞台，左右信息轨和中央战场共同缩放，而不是在网页内容卡片中滚动。
- 左侧只承担选中卡详情；右侧固定承载双方状态、事件记录和当前操作。
- 手牌与场上卡的可用动作就地出现，减少视线在卡牌和底部操作条之间往返。
- 阶段轨保持在双方战场中线，攻击、响应、公开展示和骰子等关键事件有独立聚焦层。
- 断线、投降、结束、返回大厅形成明确闭环。

### Hero-Rush 当前问题

| 优先级 | 问题 | 影响 | 所需层级 |
| --- | --- | --- | --- |
| P0 | 线上事件此前被 reducer 丢弃 | 玩家无法理解服务器刚执行了什么 | 前端；本轮已保留并显示最近 80 条 |
| P0 | 主卡组、冲击卡组和隐藏卡此前使用临时色块 | 两类牌堆无法识别，也不符合官方素材 | 前端；本轮已接入官方卡背 |
| P1 | 动作集中在底部全局条 | 目标卡与动作距离远，移动/号召按钮数量多时难扫读 | 前端上下文动作重构 |
| P1 | 攻击与响应没有中央聚焦层 | 玩家难以识别攻击者、目标、距离和当前优先权 | 前端，必要时补充投影字段 |
| P1 | 没有完整胜负结果层和返回大厅动作 | 对局结束后缺乏产品闭环 | 前端、协议状态 |
| P1 | 小屏仅继续缩小，缺少 Legion12 的可滚动画布策略 | 低分辨率下卡牌和文字不可读 | 前端响应式舞台 |
| P2 | 右侧只有抽象流程，没有可点击的卡牌事件记录 | 复盘最近操作困难 | 前端；本轮已加入基础记录，后续补卡名解析 |
| P2 | 撤退区、虚空区和结附区只是小格堆叠 | 卡多时无法浏览或选择目标 | 前端区域弹层 |

### 对战界面验收目标

- 主卡组统一使用黑色卡背，冲击卡组统一使用白色卡背；隐藏手牌和覆盖卡使用主卡组卡背。
- 右侧事件记录始终可见，并显示玩家、动作、数量和涉及卡名。
- 选择手牌或场上角色后，首要动作在卡牌附近出现；底部只保留跨区域确认和阶段结束。
- 攻击阶段中央显示攻击者、目标、距离、战力与当前响应方。
- 对局结束显示胜负、原因、对局编号和返回大厅。

## 四、推荐实施顺序

### M5.1：信息反馈与真实牌堆（当前批次）

- 接入两张官方卡背。
- 线上客户端保存服务端事件并显示对局记录。
- 补齐实战连接状态和投降入口。
- 修正大厅默认模式、普通玩家入口和沙盒说明。

### M5.2：上下文操作与战斗聚焦

- 把号召、基地部署、移动、起动效果拆成卡牌就地操作。
- 新增攻击/目标/响应聚焦条。
- 为撤退、虚空、结附增加可浏览弹层。
- 新增胜负结果层。

### M5.3：权威沙盒命令

- 新增 `SANDBOX_COMMAND_V2` 协议与服务端权限校验。
- 建立添加卡牌、区域移动、阶段跳转、数值修改等稳定命令。
- 每条命令写 journal、返回事件和状态哈希。
- 支持导出与重放。

### M5.4：好友房整备室

- 新增房间状态消息、准备/取消准备、离开/关闭、卡组锁定和规则选项。
- 完成整备室 UI 与双方状态同步。

## 边界说明

Legion12 的“主宰、士气、天灾、前后排”属于其自身规则，不能搬入 Hero-Rush。Hero-Rush 继续使用 1.02 规则定义的先锋、侧翼、后卫、基地区、时间线、虚空区、撤退区、主卡组和冲击卡组；只借鉴 Legion12 的固定舞台、信息轨、就地操作、事件反馈与沙盒调度机制。
