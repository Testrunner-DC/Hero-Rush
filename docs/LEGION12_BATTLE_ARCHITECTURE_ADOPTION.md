# Legion12 对战架构学习与 Hero-Rush 落地
## 学习边界

本轮直接追踪了 Legion12 本机代码中的大厅、`GamePage`、`GameBoard`、`PlayerMat`、`PromptOverlay`、`GmPanel`、网络状态层，以及服务端 `L12RoomManager`、`L12GameEngine`、GM 命令处理与记录器。Hero-Rush 只借鉴行为与架构，不复制术语、颜色或视觉资产。

## 真正需要继承的结构

1. 路由页面是薄壳。战场、提示、GM 和连接恢复各自维护明确职责。
2. 观察方向与当前操作者分离。上下方玩家不会因为操作权变化而翻转；沙盒根据待处理决定、流程行动方与优先权动态决定命令 actor。
3. 浏览器不直接修改局面。正式对战和沙盒普通操作都进入同一个权威规则内核；GM 操作走单独的特权原子通道。
4. 可操作性来自服务端状态。`pendingDecision`、`availableActions`、战斗上下文和公开投影决定高亮与按钮，页面不猜规则。
5. 每个房间串行处理命令，以 revision 和 state hash 防止并发覆盖；断线后恢复同一状态，而不是重新开局。
6. GM 操作必须被验证和记录。接受与拒绝都形成轨迹，便于复盘规则、定位卡牌效果和复现问题。

## 本轮已落地

- 沙盒命令进入服务端串行队列，和正式对局一样避免同时写入状态。
- 新增 `SANDBOX_RESUME_V2`：在断线宽限期内使用 V2 身份恢复同一沙盒、revision、全公开视图和审计轨迹。
- 客户端加入旧 WebSocket 消息隔离、25 秒心跳、单调 revision 接收和恢复失败后的安全重建。
- 服务端为规则命令、GM 原子和拒绝命令保留结构化审计日志；恢复时一并返回。
- GM 面板新增公开卡目标选择、撤退与场上移动；这些操作调用服务端原子机制，不在前端伪造局面。
- 战场继续使用固定 `orientationSeat=0`，命令 actor 则由待处理决定/流程动态计算，落实“固定观察席位 + 动态操作者”。

## 后续架构批次

1. 将沙盒审计由内存日志接入持久化存储，并增加 JSON 导出与复现入口。
2. 扩展服务端 GM 命令：指定卡生成、区域放置、数值/资源、触发开关、战斗构造；每项保持事务式验证。
3. 为 `BattleViewV2` 增加服务端计算的具体合法目标，而不仅是命令类型；战场直接显示目标和落点。
4. 将效果决定映射到战场卡位，减少底部通用弹层；加入可最小化提示和等待方的非泄密状态。
5. 从战斗上下文生成攻击线、攻防数值与应对阶段反馈，并把事件日志过滤成可复盘的玩家决策和结果。
